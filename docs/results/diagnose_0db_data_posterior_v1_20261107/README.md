# 0 dB Data 后验/相位变体筛查（2026-11-07，2026-11-19 修正 EM 评分）

状态：**开发机制筛查，不是确认。** 变体共享同一 episode/波形；只有 `oracle` 使用 Data 标签（真实符号错误），其余只用接收波形、模型 soft 输出与估计 CIR。

> **2026-11-19 修正**：旧版 EM 循环在最后一轮 CIR 更新后没有再重解码，导致 EM2/EM3 的 BER 与 tail 对应倒数第二次更新后的 CIR（EM3 落后两步），而 NMSE 和跨帧状态已用最终 CIR。现改为每轮“Data 后验 → 重解码”，最后一轮更新后也用最终 CIR 重解码。`soft`/`oracle`/`block_phase` 的 BER/NMSE/gain 逐位一致（仅 `elapsed_ms` 随运行变化）；EM2/EM3/EM+block 数值已更新。旧版见 git 历史。

## 协议

- 配置：`configs/eme_long_memory_v2_online_dd_tail_v1.json`；强离线 checkpoint SHA256 `8cd3912d1c957c9689c51730aff9d27a8f74942186c802a7483e5781af65aec4`。
- 开发 seed：140001–140002；每 seed/SNR 16 帧；0/5/10/15 dB。
- 变体：
  - `soft`：当前 Data 后验（`R_t = σ² + Σ|h|²Var`）；
  - `oracle`：真实符号错误的 R_t（仅诊断）；
  - `em2`/`em3`：Pilot 后验后做 2/3 次“Data 后验 → 模型重解码”；
  - `block_phase`：逐块 DD 相位后再做 Data 后验；
  - `em_block`：EM + 逐块相位。
- **时序说明**：变体的 BER 使用当前帧更新后的 CIR 重新解码当前帧，属于**同帧重解码（transductive turbo）**；已确认的 Bayes 是**跨帧因果**（当前帧后验用于下一帧）。同帧版本合法（块已完整接收、不读标签），但属于新的时序协议，需要单独报告。

## 判断

1. **0 dB 的 H3 斜率不是数据后验/相位能修复的**：所有变体的斜率仍为负；最好的是 EM2 `−0.0095`、oracle `−0.0109`、EM3 `−0.0118`（soft 为 `−0.0152`）。
2. **0 dB 不是增长**：`soft`/`oracle`/`block_phase` 仍是“早期高 → 第三窗负 → 第四窗正”；EM2/EM3 修正后第三窗转正（`+0.0039`/`+0.0194`），但首窗最高、整体斜率仍为负，属于早期收敛后的波动，不是持续增长。**0 dB 应表述为“早期收敛/后段饱和且晚窗为正”**；5/10/15 dB 才支持增长。
3. **修正后 EM3 的 0 dB 改善两 seed 同向**（`+0.0387 / +0.0269`），EM2 仍偏 seed 相关（`+0.0372 / +0.0148`，140002 接近 soft）；EM+block 在 0 dB 反而低于 soft。EM3 的优势仍是 2-seed 开发筛查，不能升级为稳定机制或确认结论。
4. **block_phase 是数值不受本次修正影响、且两 seed 同向的小改善**：`+0.0151 / +0.0254`；5/10 dB 接近 soft（5 dB `−0.00036`、10 dB `−0.00008` 相对 soft）；成本约 1.35 s/帧。
5. **5/10 dB 的 soft 仍最好**；EM2/EM3 略差；15 dB 两个 seed 的 Bayes 都略差于 Frozen，与 10×128 相反，属于 session 噪声。
6. **误差 lag-1 约 0**：0 dB 错误不显著自相关；EM 的收益主要来自“更新 CIR 后重解码”，不是误差相关模型。
7. **成本**（本机 GTX 1650，本次运行）：soft/block ≈1.35 s/帧、EM2 ≈2.47 s、EM3 ≈3.12 s、EM+block ≈2.47 s；102.4 ms 帧预算下均不实时。
